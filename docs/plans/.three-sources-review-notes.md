## Gaps, blunt

**Re-pull semantics for `facility_meetings` are undefined — the single biggest hole.**
The proposed UNIQUE key is `(term_code, crn, meets_on, starts_at, ends_at, room)`. Every field is in the key, so a meeting that moves room or hour inserts a *new* row and the old one survives for ever. §2.3 specifies write semantics for `asked`/`silent`/`gone` at the **section** level and says nothing at all about meetings. A second pull after the registrar moves one class manufactures a permanent phantom clash against a meeting that no longer exists — in the exact code path (`_overlap`) the plan is selling as free. There is no delete-and-replace rule, no `pull_id` on the meeting row, no reconciliation test.

**No parsing or timezone contract for `EVEN_START` / `EVENT_END`.**
The plan names the columns and the portal's typo, then never says how one portal value becomes `meets_on` + `starts_at` + `ends_at`, in what timezone, or how that lines up with the Hub sessions `_sessions` currently builds (`str(session.get("date"))`, `start`, `end`). `group_clashes._overlap` compares `one.date != other.date` as **raw strings** and `_minutes` splits on `:` — a one-hour or one-day offset silently changes every clash count and every handover date range, and Stage 2 mixes the two sources into one comparison. Nothing in six stages tests that a facilities session and a Hub session for the same meeting produce identical `Session` tuples.

**Stage 2 and Stage 3 are both gated on the Hub, which the plan never states.**
`read_publication` (`backend/sorbonne/api/publication.py`) takes `client: StudentPlatformClient = Depends(require_client)` and calls `client.list_sections` before it ever reaches `_sessions`. Swapping the session source does not decouple the clash panel from the Hub — with the platform unconfigured the whole route still fails and there is no clash panel to improve. `registration_check` iterates `self.term_links()`, so Stage 3's student clashes only exist for a term someone has linked to a Hub semester. The plan's whole premise is a third source that stands on its own; both stages that consume it are locked behind the second.

**The openToAll quirk defeats Stage 2's headline claim, and it is buried in D4.**
`term_publication` joins `cohort_scopes s JOIN student_cohorts c ON c.id = s.cohort_id` and returns one entry per **owning** cohort. `_clashes(cohort, groups, sessions)` therefore compares a shared LANG group only against the blocks of whichever cohort happens to hold its row. A student of cohort B in a LANG group filed under A gets no clash check against B's own lectures — the third recurrence of the bug the brief says has already bitten twice. The plan mentions this once, as a subordinate clause inside D4's recommendation about language levels, and schedules no work for it. "Clashes start telling the truth" is false for the shared sets while `term_publication` stays cohort-keyed.

**I19 is misdiagnosed and its actual feature request is never answered.**
The plan calls it "confirmed bug", splits it Stage 0 (copy) / Stage 6 (deletion rule against scope ownership), and never determines what happens — which is literally what the item asks. What happens: `set_cohort` deletes `WHERE student_id = ANY(:ids) AND cohort_id <> COALESCE(:cohort_id, '')` — it keys on **`group_assignments.cohort_id`**. Placement writes that column as `self._cohorts_of(...).get(student_id, cohort_id)` (`student_database.py:674`, `:722`), so a cohortless student placed into cohort X's scope already carries `cohort_id = X` (or NULL). Moving them into X deletes nothing. `costOfMove` keys on **`student.cohortId`** and counts every group whenever `student.cohortId !== target`. That divergence is the whole bug: the server already retains the groups, the warning lies. The user's actual ask — retain groups when there are no clashes — needs no deletion-rule rewrite and no Stage 6; it needs the frontend to ask the same question the server asks. Nothing in the plan says this.

**The registration blind count is argued for and then never scheduled.**
§1.3 grafts it in and says it "earns its keep before any facilities work" because `registration_check` silently skips every student not in `pulled`. Stage 0 doesn't contain it. Stage 2 adds `blind` to the *clash* payload only. Stage 3 adds `registration.none_at_all`, which is a different thing. The one piece of the validation-engine proposal the plan claims to keep is unassigned to any stage.

**I05's actual question is unanswered.** The item asks *where should this live*. The table answers `frontend/src/services/groupWalk.ts (new)` — a service file, not a surface — and D4 only settles whether languages get seated. No page, no entry point, no relationship to `PlaceInBlock` (I13) or `FillBlock` (I08), which are the two existing surfaces it would obviously belong to and which the plan schedules into the same Stage 6 without saying whether they are one feature or three.

**I22's answer is wrong on the query it uses as its own example.** "Physics student in L3 on a Tuesday for languages" needs `meetsOn` and `sets` to be *correlated*. `tableFilter` composes column clauses with AND across independent columns, so a `sets ∋ LANG` + `meetsOn ∋ Tue` row matches a student who takes languages **and** has something (anything — MATH) on Tuesday. The plan asserts "three of the four clauses work today" and "the gap is two columns on the row, not a new language". The gap is a join, and two flat columns cannot express it.

**I17/I24 sequencing is backwards.** Stage 1 introduces the longest, most failure-prone sync in the product — 165 sequential-ish calls at concurrency 2 with a mandatory retry — while timeouts, retries and cancel (I17) and the single-error-message fix (I24) sit in "Stage 6, optional, on demand". The plan's own §6 says an old extension silently recording 165 CRNs as `silent` is the failure mode the feature exists to prevent, then defers the machinery that would surface a stalled or half-finished run.

**No regression tests named for five "confirmed bug" fixes.** AGENTS.md working agreement #4: for a bug fix, add a failing regression test first. Stage 0 fixes I07, I09, I11, I14, I19 and the dismissal prune, and names not one test. Stage 1 is the only stage with "tests that are the point".

**New verdicts land in a surface with no dismissal story.** §2.5 defers the severity ladder on the grounds that everything lands in an existing surface. `RegisterBanner` buckets are not dismissable — there is no dismissal key family for CRN-subject verdicts at all. Stage 1 therefore adds a permanent 30-line `noTimetable` list to an undismissable amber banner that also drives `attention`. The plan predicts this ("when the `noTimetable` list stops shrinking and starts nagging") and schedules no remedy. Same for Stage 2's `blind` list and Stage 4's `teacherDiffers`.

**The extension re-implements the column allowlist outside the mechanism that exists to hold it.** §2.2 correctly rejects forcing `GetTimeTable` into `GRIDS` — then puts the column allowlist "in the handler". `grids.js` opens by stating that bounding which columns may come back is the extension's privacy boundary, with a worked example (a teacher's personal e-mail and Oracle id). Moving that boundary into a hand-written `case` in `background.js` splits the review surface in two, and the plan gives no test asserting the timetable handler's allowlist. Related: it never says whether the 43k-row payload is de-duplicated **in the extension or on the server**, which decides both whether `MAX_ROWS = 20000` (`background.js:39`) truncates a term's pull and where `head_count` is computed.

**D1 reinterprets a stated constraint on its own authority.** The brief says production data loads go through the app's own API, never direct DB access to prod. The plan's recommendation is `pg_dump` from a Neon branch, justified by "the rule governs writes". That may well be right, but it is presented as a recommendation with a conclusion already drawn rather than as the constraint waiver it is, and nothing in AGENTS.md mentions Neon branches or that anyone has prod credentials locally. Note also that pytest fixtures deleting `sorbonne_test` tables is asserted with no citation.

**Stage 5's estimate contradicts its own description.** "1 day" for a handover detector *plus* changing `group_crns`' primary key on a live production table with a tested backfill — which the same paragraph says needs "its own release, its own tested backfill". Pick one.

**Two overstated code claims.**
- "`describeMismatch` is an exhaustive switch with no `default`, so TypeScript names every site." Under `strict: true` a new `Mismatch.kind` errors in **that one function**. Downstream is untouched: `registrationWarnings` takes `kind: string` and maps everything to `Warning.kind = "registration"`, so no call site is forced to handle a clash differently from a missing registration.
- "`sets` on `StudentRow` (~10 lines)". `StudentRow.groups` is populated from a cohort-keyed read; a shared set's members are not in the owning cohort's `students` list (`term_publication`), so a `sets` column that includes languages is the same openToAll problem again, not ten lines.

**Nobody thought about:**
- **Who owns the 44 out-of-SCEN elective sections.** Stage 3 says an ours-vs-elective clash is "fixed by moving a student, or escalated". Escalated to whom, through what surface, recorded where? A SCEN coordinator cannot move a student out of an ENGL section. Without an owner this is 31 students' worth of permanent, unactionable red.
- **Whether pulling timetables for non-SCEN sections is in scope of what the coordinator may read from the registrar portal.** The plan expands the pull from SCEN's own CRNs to every CRN any SCEN student is registered in and treats that as free.
- **`head_count` degenerate cases.** rows ÷ meetings assumes every student attends every dated meeting. A mid-term add/drop, a single cancelled meeting, or zero published meetings makes the ratio non-integral or a divide-by-zero. The plan calls the invariant verified "with zero exceptions" across 135 sections and specifies no guard for the first exception.
- **What `PortalRegistrations` costs on mount:** one `registration-check` request per cohort, `retry: false`. Stage 3 makes each of those queries strictly more expensive (clash computation per cohort) with no caching or batching note, on a page that already fires N of them before the user has picked a cohort.
